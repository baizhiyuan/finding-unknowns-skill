# Field notes: small-model deployment on a Jetson Xavier NX (home-nas)

Real run, 2026-11-10, finding-unknowns v4.2.0 (installed copy), on the author's own
infrastructure repo `baizhiyuan/home-nas`. Status: **paused** after the plan; the device
was unreachable (see "Resume point"). These notes record skill defects observed in the
field. Nothing here has been fixed yet; fixes go into a patch release once there is
evidence from the rest of the run.

## What ran

1. Phase 0 routing: UU first (Jetson constraints), then KU (purpose, model). Prior stated
   before discovery: "`platform/jetson/` exists, so this is just an aarch64 CUDA container
   added as a new stack."
2. Technique 1 via `blindspot-scout` (compact report), read-only on the repo, no device
   access. The prior was contradicted in five places: the Jetson is no longer the NAS (the
   Orange Pi 5B took over on 2026-11-03), the roadmap already plans a Jetson AI node,
   `platform/jetson/` holds only `daemon.json`, `bootstrap.sh` refuses some modes on the
   Jetson, and an earlier GPU attempt (Immich) concluded "don't". 10 of its citations were
   spot-checked; all matched.
3. Technique 3 interview, two rounds (AskUserQuestion). Decisions: LLM first, then
   whisper; the Jetson becomes a dedicated AI node (rollback role dropped); success =
   usable and fast enough.
4. Technique 5 plan with a Definition of verified, and a theory-vs-result prediction
   recorded before any measurement (see Resume point).

## Defects observed

### F1 — The scout missed a fact recorded in the repo

- **Observed:** the scout reported "the exact JetPack/L4T minor version is recorded nowhere
  in the repo (needs device check)". `docs/_drafts/Immich-GPU-可行性.md:14` states
  "JetPack 5.1.5 是 CUDA 11.4 / Ubuntu 20.04". The scout had read and cited that same file
  for other claims.
- **Why it matters:** a "needs device check" label on a fact that is already in the
  territory sends the user to do work the repo already answers, against the skill's own
  rule "never ask what the territory can answer".
- **Candidate fix:** in `blindspot-scout`, before labelling anything "not in the
  territory" / "needs device check", grep the territory for it (versions, hostnames,
  limits) and cite the hit or state the search that came back empty.

### F2 — A follow-up prior from the user was not treated as a prior

- **Observed:** after the report, the user asked whether the Jetson could be upgraded to
  Ubuntu 26.04, or use Anaconda, "so it can run the newest models". That is a second
  prior (upgrade the OS → newest model support). The skill has no rule for priors that
  arrive mid-discovery; the orchestrator verified it ad hoc (web search: JetPack 6 is
  Orin-only, Xavier NX tops out at JetPack 5 / Ubuntu 20.04; CUDA can be upgraded
  separately from JetPack 5.0.2; model support depends on the runtime, not the OS). It
  was contradicted.
- **Why it matters:** surprises against a prior are the skill's most valuable output, and
  a late prior is often the one the user is most invested in.
- **Candidate fix:** Execution_Policy / Phase 0: "A prior stated later (a follow-up
  question that assumes an answer) is recorded and checked like the first one; report
  it as a Surprise when contradicted."

### F3 — Reachability of the territory was not treated as an unknown

- **Observed:** the plan's first step was read-only checks on the device over SSH. The
  blind-spot pass never asked whether the device could be reached from the machine doing
  the work. In practice the local Tailscale client could not reach the coordination
  server, no peer answered `tailscale ping`, and `~/.ssh/config` had no entry for the
  Jetson; the run stopped there.
- **Why it matters:** for any task on remote hardware or services, access is a landmine
  with the widest blast radius: every later step depends on it.
- **Candidate fix:** add to Technique 1 (and the domain-checklist hook) for work on
  remote devices/services: "Can the agent reach it from here, with which credentials?"
  (cheap check: port probe / ping, SSH config entry), reported as a finding or a
  `needs device check` row before the plan relies on access.

## Resume point

- **Device:** `jetson-nas` (Tailscale 100.125.87.97), LAN `jetson-nx` 192.168.31.66.
  Login user not recorded in the repo or in `~/.ssh/config`.
- **First step:** read-only checks (`/etc/nv_tegra_release`, `free -h`, `nvpmodel -q`,
  earlyoom, PM2, `df -h`, CUDA version, `tegrastats`).
- **Plan:** keep JetPack 5.1.5 (no reflash; a reflash needs its own confirmation);
  native llama.cpp built with CUDA for sm_72 (11.4 first, CUDA 12.x via the upgradable
  compute stack only if the build fails); one 3B Q4_K_M model; `llama-server` under
  systemd; earlyoom exemption; weights via hf-mirror.
- **Frozen acceptance threshold (user-approved before measuring):** 3B Q4 decode
  ≥ 5 token/s, median of 3 `llama-bench` runs at MAXN.
- **Prediction (written before measuring):** 6–12 token/s decode for 3B Q4. Basis: memory
  bandwidth ≈ 59.7 GB/s and ≈ 2 GB of weights give a ≈ 30 token/s ceiling; llama.cpp
  usually reaches 20–40 % of it. Confidence medium; run-to-run noise expected within
  ±10 %. If below 5: check, in order, that the build uses CUDA, the power mode is MAXN,
  memory is not swapping, and only then the prediction itself.
