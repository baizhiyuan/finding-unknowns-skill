# 5.0 design: one task card, kept by the person and the agent

Status: **proposed** (2026-11-11). This document is reviewed and merged before any 5.0
code changes. The 5.0 work then lands on a `v5` branch and is merged to `main` only after
the Stage 0 evaluation below has run.

## 1. Why 5.0

Three blinded, pre-registered evaluations ([pilot](../evals/2026-11-10-codex-pilot/README.md),
[v2](../evals/2026-11-11-v2-cross-model/README.md), [v3](../evals/2026-11-11-v3-hook/README.md))
measured these skills as a boost to model output on single-turn tasks.

- **Gain:** none that replicated. The tasks had about 2–3 traps of headroom out of 25.
- **Cost:** roughly +10 % to +70 %, with longer answers and more small false claims and
  overclaims.
- **Narrow effect:** one recurring effect, "say what the checks did not prove" catching a
  self-updated snapshot test (H4). It was seen on Sonnet only, in 4 of 5 invoked runs
  against 1 of 12 other runs. It is a post-hoc pooled subgroup, so by this repository's
  own rule it is a `post-hoc fit`, not a finding.
- **Not exercised:** no arm ever took an unsafe action, so the irreversibility floor was
  never tested. The result cards sat at the ceiling.

The author's goal was never model output alone. It is the person's side:

- understanding what is being done and why, and judging it critically;
- not being interrupted constantly;
- having wrong expectations corrected in time;
- not losing track on long tasks;
- learning from the work.

None of that has been tested. 5.0 rebuilds the plugin around that goal and says plainly
that its value is a hypothesis until a human evaluation supports it.

Every component kept below is kept **on design grounds**, not on evidence. Only one
sentence-sized piece has even weak evidence, and §8 tests it directly.

This design follows the advisor review by Fable 5.2. GPT 6 Astra was also consulted.
Their briefs and answers are kept outside the repository; §10 lists where 5.0 departs
from the Fable review.

## 2. The organising idea: a task card

A three-phase loop (Brief → Quiet build → Debrief) fits a single session. It breaks in
the two cases that matter most:

- **Multi-session work:** phases do not survive a session boundary; files do.
- **Research:** one brief is followed by many results over days.

So the unit of 5.0 is a **task card**: one Markdown file per task. The brief is frozen at
the top and append-only deltas go below. Every command is an operation on the card:

| Command | Operation |
|---|---|
| `/brief` | Create the card: discovery, predictions, stop-points, contract. Freeze it. |
| `/catch-up` | Read the card: what changed since you last looked, recall questions, next decision. |
| `/debrief` | Close predictions against evidence; record what changes in your model. |

Phase changes follow file state, not model judgement. If an open card exists, work
continues from it.

## 3. The card

**Path:** `.finding-unknowns/tasks/{slug}.md`.

**Committed by default.** When the brief freezes, the agent commits the card alone, as
`chore(card): brief {slug}`, using pathspec-only `git commit -- <card>` so the user's
staged work is not touched. The user can decline once per project. The commit hash is
tamper-evident timing for the predictions. Without git, the card records a timestamp
and is labelled `timing: self-reported`.

**Detail logs** go to `.finding-unknowns/logs/`, which is the only gitignored path.

**Live part:** at most about 40 lines, not counting the frozen Brief.

```
# {task}
Goal: {one line} · State: {briefing | building | waiting on you | debriefed}
Next decision that needs you: {one line, or "none"}
Mode: {ship | learn} · Last seen by you: {date, delta #}

## Brief (frozen {date}, commit {hash})
Approach: {choice} because {one-line why}
Your predictions:  P1 … (confidence) · falsifier · should not change
Agent predictions: A1 … · falsifier · should not change
  (or: "No real prediction here; contract only")
Stop-points: {the only reasons work will stop for you, §4}
Contract: | claim | check (can fail) | does NOT prove | lane |

## Deltas (append-only, one line each, pointer to evidence)
D1 {date} deviation | surprise | decided-for-you: … → {path:line | log}

## Model changes (at most five live lines)
You expected X → it is Y, because Z  [shown, not confirmed | confirmed]

## Open
{unchecked items, pending decisions, pending runs}
```

Rules:

- **Predictions are separate from contract checks.** "The tests will pass" is something
  the agent makes true; it is a contract check. A prediction is a claim about something
  the agent does not control:
  - where the bug is;
  - how many callers break;
  - a benchmark number;
  - an experiment outcome.

  Many engineering tasks have none. Then the card says "No real prediction here;
  contract only". Requiring a prediction on every task manufactures ceremony.
- **Every prediction has a falsifier and a "should not change" half.**
- **The person predicts first.** One skippable question in ship mode, up to three in
  learn mode, each with a confidence. The agent's prediction is shown only after the
  person answers, so the person is not anchored. "No idea" is a valid answer.
- **Re-brief instead of drift.** When a Brief premise dies, the card is amended: a dated
  line is added and the old line is kept. A Debrief never compares against a dead brief.
- **Keeping it short:**
  - Each session's deltas roll up into three lines at the session's end.
  - `/catch-up` shows only what changed since the "Last seen" marker, so the cost of
    getting re-oriented grows with the change, not with the history.
  - Detail goes to `logs/`; the card holds pointers.
- **Explanations shown are not explanations understood.** A model change stays
  `shown, not confirmed` until the person confirms it.

## 4. Stop-points: what may interrupt

Work stops for the person only on conditions that can be checked against the card,
never on the agent's judgement of stakes:

1. **Irreversible action:** an action in an irreversible class (data rewritten or
   dropped, deletion, production data, money, external publication, commitments to
   people). The **build rule** applies: the agent prepares the exact command, the
   person runs it or gives a yes for that specific command, and the post-check runs
   before the item closes. A general "go ahead" is not a per-command yes. Classify
   upward when unsure.
2. **Scope change:** anything outside the Brief's approach or contract.
3. **Dead premise:** a Brief premise or a prediction's falsifier has fired, and no
   reversible path remains. (v2's H5 and the Jetson field note are both this case.)
4. **Budget:** a resource or time overrun past the multiple agreed in the Brief.

Everything else is written to the card as a delta and taken in at `/catch-up` or
`/debrief`. Reversible choices take the most reversible option and are logged as
`decided-for-you`. Questions that are not urgent wait in Open until the next stop.

## 5. Learning

- **Teaching happens at the point of error.** The Brief gives one sentence of "why" per
  decision, with more on request. The real explanation goes in the Debrief, on the rows
  where a prediction failed, the person's own first.
- **Depth is set by predictions, not self-report.** `ship | learn` is asked once per
  project and stored in `.finding-unknowns/profile.md`. After that:
  - a correct, confident prediction skips the explanation;
  - a wrong prediction gets one.
- **No quiz gate.** The 4.x must-pass quiz and "comprehension is the merge gate" are
  removed. Instead, `/catch-up` asks recall questions **before** showing the card, so
  that recall is practised and a stale brief shows up:
  - drawn from the deltas and the wrong predictions;
  - two or three in learn mode, one skippable question in ship mode;
  - a two-sentence teach-back is accepted in place of the questions.
- **The prediction habit is the core of the loop.** In 4.x it sat buried in
  keep-the-reasoning's Practice mode. Before asking, write what you expect; afterwards,
  name one thing that was not checked.
- **The prediction log is a learning record.** Each closed prediction appends a line to
  `.finding-unknowns/predictions-log.md` with the date, task, owner (you or the agent)
  and verdict.
  - The person's hit rate over time is a learning signal.
  - An agent hit rate near 100 % means its predictions are too soft.

## 6. Research work

The unit is the **claim**, which outlives many runs. `theory-vs-result` stays a separate
skill. It is the research core of 5.0, and the card's Debrief uses its verdict and tier
vocabulary. 5.0 adds the following:

- **The Brief for a claim is the prediction card**, with three additions:
  - the person's and the agent's predictions on separate lines, since their disagreement
    is the most informative row;
  - a **stopping rule**: how many seeds or runs before any verdict;
  - a noise floor **measured before the rule is frozen**, from at least three reruns or
    an A/A comparison. With fewer, the card says the floor itself is uncertain. v2 is
    the cautionary case: a rule built on two runs called +2.5 "signal", and v3 reversed
    it.
- **Results over days:**
  - Each claim gets an append-only run table: date, config, what changed, result,
    cumulative trials, data spent.
  - Each run gets a one-line Note card.
  - The full Debrief runs only at the declared stopping point. Until then the state reads
    "3 of 5 seeds done, no verdict yet". Peeking at noisy interim results is research's
    version of an interruption.
- **When the person's hypothesis is under test**, the agent's pull is to rescue it. The
  two-verdict rule protects against that:
  - the rule verdict is mechanical;
  - the direction verdict is proposed by the agent and owned by the person;
  - the Debrief quotes the person's own words from the frozen card.
- **Kept unchanged:**
  - the trials and data-budget lines;
  - `post-hoc fit`, `void`, `descriptive only`;
  - the mismatch walk (pipeline → comparison → metric → theory → environment);
  - the Debug path;
  - `untraceable` for numbers that cannot be found in the artifacts.

## 7. Debrief honesty when one agent wrote both halves

The guard is structural, not a promise of self-criticism.

- **Frozen predictions are quoted verbatim by ID.** The Debrief never restates them.
- **A fresh context grades them.** `mechanism-auditor`, generalised from its 4.x role,
  receives the frozen card and the artifact paths, not the build transcript.
  - It fills the Consistent? column for every prediction.
  - The builder writes only the Mechanism, with its tier.
  - Without subagents, the grading is labelled `same-context — weaker`.
- **The person's prediction is the one that cannot be gamed.** It is graded first.
- **Default length is no longer than a plain answer.** In v2 and v3 the skill arms
  wrote 22–54 % more words and made more false claims. For a human reader that cost is worse
  than for a grader. The default view fits one screen; detail comes on request.
- **The evidence block** is the compact handoff packet from 4.x keep-the-reasoning:
  1. the commands actually run and their trimmed output;
  2. what each check did **not** prove;
  3. what was not checked (never empty).
- **Surrender signals** are named once, plainly, and then the person decides. The four
  signals:
  - approval with no question about any listed decision;
  - the agent's own tests offered as the only evidence for the agent's own code;
  - "just tell me what to do" on a decision that affects others;
  - reasoning from another agent's summary instead of the source.

## 8. Evaluation

### Stage 0: simulated users, mechanism only (before merging 5.0)

- **Design:** six tasks, three runs each, three arms.
  - **Plain:** no plugin.
  - **60 words:** the text below in `CLAUDE.md`, no plugin.
  - **5.0:** the full plugin.
- **Who writes the tasks:** someone other than the author. Here a different model
  family writes the tasks, the hidden scripts and the scoring keys from a one-page spec,
  and the eval README discloses how independent that really is.
- **The scripted user holds:**
  - two unstated requirements;
  - one confidently stated wrong belief;
  - limited patience;
  - a premise that dies mid-build;
  - one irreversible step;
  - one prediction that the territory will falsify.
- **Measures**, mechanical where possible:
  - the misconception named before any edit;
  - requirements elicited;
  - questions the repository could have answered;
  - interruptions outside the four stop-points;
  - the irreversible step left to the user;
  - the failed prediction marked inconsistent, with the frozen card unedited (hash
    check);
  - debrief length and false claims;
  - zero overhead on a trivial control task (the C6 guard).
- **Kill rule (pre-registered):** if full 5.0 does not beat the 60-word arm beyond the
  measured noise, the plugin text is not the active ingredient. Then the 60 words ship
  as the recommended setup and the plugin is described as optional.
- **H4 check:** one fixture repeats v2's H4 shape on fresh code, to test whether the
  single sentence "say what each check did not prove" reproduces the effect.
- **Limit:** Stage 0 says nothing about comprehension or learning.

The 60-word arm (draft, frozen in the Stage 0 pre-registration):

> Before building, ask me to predict the outcome, then give yours; write both, with what
> would prove each wrong, in `.finding-unknowns/tasks/`. While building, stop only for
> irreversible steps, scope changes or a falsified premise; log other deviations there.
> Afterwards, grade each prediction against the evidence and say what each check did not
> prove.

### Stage 1: people, the actual claim

- **Who:** 8–12 participants other than the author, for example the author's classmates.
- **Design:** a within-subject crossover, counterbalanced, comparing plain Claude Code
  with 5.0. There are two matched tasks of about 45 minutes each on an unfamiliar
  repository:
  - an engineering task with a planted wrong premise and tests that prove nothing at
    handoff;
  - a small, noisy experiment where the intuitive hypothesis is wrong.
- **Primary outcomes (pre-registered):**
  - the accept or reject decision with its reason, graded blind;
  - a six-item test 48–72 hours later, without materials, written beforehand by a third
    party.
- **Secondary outcomes:**
  - calibration (predicted score minus actual score);
  - whether the planted belief persists;
  - the participant's time and annoyance;
  - voluntary use of `/brief` in a free week afterwards.
- **Verdict rule:** show every pair. With eight people, only 7–8 pairs in one direction
  can be told apart from chance; anything less reads "can't tell, run eight more".
- **What would show the idea is wrong:**
  - no delayed gain;
  - a gain, but nobody uses it voluntarily;
  - confidence rising without accuracy. This is the worst case: cognitive surrender with
    better paperwork.
- **Author diary:** the author's own diary on real tasks, kept in alternating weeks with
  a write-from-memory check before reading the card, is recorded as descriptive only.

**Skill descriptions** use phrases people actually say: "brief me", "catch me up",
"where were we", "did it match what we expected". Generic verbs such as "plan" or
"review" would fire on trivial tasks. v3's 15/15 activation came from task-specific
descriptions, not generic ones.

**The token rule:** the scarce resource is the reader's attention.

- **Worth spending on:** the card, delta lines, raw evidence, and explanation at the
  point of error.
- **Waste:**
  - skill text loaded on trivial tasks;
  - score tables;
  - a rule stated three times (policy, steps, checklist);
  - any sentence for the person that changes neither a decision nor the person's model.

**Hooks:** a SessionStart hook that prints the card header only when an open card exists
is worth testing later. It is not part of 5.0: v3's reminder hook did not help, and this
one is untested.

## 10. Where 5.0 departs from the Fable review

- **`/catch-up`, not `/status`.** Claude Code has built-in `/status` and `/resume`
  commands, so either name would collide. "Catch me up" is the phrase the review itself
  suggests.
- **quiz-master is kept, but demoted.** The review demotes the quiz from a gate to a
  tool and does not list the agent for deletion. It now only generates recall questions.
- **The person can decline the card commit.** The review flips the default to
  committing the card. 5.0 keeps that default but asks once per project, because the
  commit lands in the person's own history.

## 11. Migration for 4.x users

- **`/cartographer`, `/blindspot`, `/change-quiz` and keep-the-reasoning are gone.**
  - Use `/brief` for the start of a task.
  - A blind-spot pass is still available inside the Brief ("blind-spot pass" or "what
    am I missing").
  - Use `/debrief` for the handoff.
- **Existing 4.x files** (`unknowns-ledger.md`, `unknowns-spec-*.md`,
  `implementation-notes.md`, `predictions/`) are read in place. `/brief` and
  `/catch-up` offer, in one line, to fold them into a card, and never move them
  silently.
- **To get 4.x back:** install from the `v4.3.2` tag.

## 12. Order of work

1. This document: review, then merge to `main`. Docs only; the version is not bumped.
2. On the `v5` branch:
   - the core skill, the card, the commands and the agents;
   - the deletions;
   - `install.sh`, `validate.py` and CI;
   - then the README, docs and the single diagram, in en and zh.

   Each step gets an independent review.
3. The Stage 0 pre-registration, then the runs and the report. The kill rule decides
   what ships.
4. Release `5.0.0`: merge `v5`, tag, and state in the README that the human-side value
   is untested.
5. Stage 1 with participants, when they have been recruited.
