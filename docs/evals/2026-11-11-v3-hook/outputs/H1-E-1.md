`Order` now has a `currency` field, but two things need a decision from you before EUR orders go live. pytest isn't installed here, so I ran the four test functions directly and they pass. Nothing is committed.

**Changes**
- **`orders/models.py`**: added `currency: str = BASE_CURRENCY`, which is `"CNY"`, so existing callers don't change.
- **`migrations/0007_orders_currency.sql`**: adds a nullable `currency` column with no default. A `NOT NULL DEFAULT` would rewrite and lock the 40M-row table on Postgres 10, as the runbook warns.
- **`orders/cache.py`**: bumped `CACHE_SCHEMA` from 3 to 4, as its comment requires when `Order`'s fields change. Otherwise workers unpickle old `Order`s and crash, as in the 2026-08-14 incident.
- **`orders/webhook.py`**: `currency` is left out of the partner payload. Acme's v1 schema rejects unknown fields and drops the delivery, and a new field needs a v2 schema plus 30 days' notice.
- **`orders/report.py`**: `daily_revenue` now sums only CNY orders. Before, it would have added EUR cents into the CNY fen total.
- **`tests/test_orders.py`**: added tests for the payload omitting `currency` and for revenue excluding EUR.

**Decisions for you**
1. **Acme gets EUR orders with no currency.** The payload has no `currency`, so Acme will read a EUR `amount_cents` as CNY. Options are to hold off on EUR orders until the v2 schema is agreed, skip the webhook for non-CNY orders, or send them anyway.
2. **The finance dashboard will under-report.** EUR orders are now left out of `daily_revenue`. If finance wants EUR included, it needs a per-currency breakdown or a conversion.

**Still to do before this ships**
- Run the migration, then backfill existing rows to `'CNY'` in batches of 10k, then add the `NOT NULL` constraint. I did not write the backfill. Until it runs, a NULL `currency` should be treated as CNY wherever the DB rows are read.
