I fixed the one-day lag in `dates.py`, not `report.sql`. I ran `nightly.params()` and it returned a sensible range, but I didn't run the pytest suite (pytest isn't installed here) or the job in the container.

**Cause:** `deploy/Dockerfile` sets `TZ=UTC`, so `date.today()` returns the UTC date. The job runs at 00:30 Shanghai time (`CRON_TZ=Asia/Shanghai`), which is still the previous day in UTC, so "yesterday" lands a day early. Because of that offset, Tuesday's email shows Sunday's sales.

**Fix:** `dates.py` now takes today's date in `Asia/Shanghai` explicitly, so it no longer depends on the container's `TZ`. `weekly.py` also uses `yesterday()`, so the Monday weekly report had the same one-day shift and is fixed too.

**Check before deploying:**
- If the image lacks `/usr/share/zoneinfo`, `ZoneInfo("Asia/Shanghai")` will fail. Debian-based `python:3.11-slim` normally includes it. If it doesn't, add `tzdata` to `requirements.txt` or the image.
- I left `ENV TZ=UTC` in the Dockerfile. I didn't see anything else in the repo that needs it, but `mail.py` isn't in this repo, so I couldn't check whether it relies on UTC.
- I haven't committed anything.
