## ranker-v7 A/B: recommendation is **do not ship**

**Checked**
- `experiment_plan.md`, `results/summary.md`, `metrics.csv`, `daily.csv` and `assignment.csv`.
- I compared the results against the plan that was approved before launch.

**Findings**
1. **The primary metric is revenue per session, not CTR.** The plan lists CTR as secondary and diagnostic. Revenue per session went from 4.82 to 4.76 (−1.2%, p = 0.21), which is not significant and points the wrong way.
2. **The latency guardrail failed.** p95 rose from 212 ms to 250 ms, which is +38 ms (p < 0.001). The limit was +20 ms.
3. **The plan's ship rule is not met.** It requires a significantly positive primary metric and every guardrail passing. Neither holds.
4. **The CTR lift is a novelty effect.** Treatment CTR was 3.85% on days 1–3, 3.65% on days 4–7 and 3.12% on days 8–14. Control stayed at 3.10%. By the second week the lift is about 0.02 points, so the 3.41% headline is an average over a decaying effect. The p = 0.03 was also one of several metrics checked, with no multiple-comparison correction.
5. **The user split looks off.** Assignment was 52,310 control and 47,690 treatment, but the plan called for 50/50. Against an expected 50,000 each, that is a sample ratio mismatch (z ≈ 14.6). This could be a bucketing or logging bug, and it casts doubt on every number above.
6. **Control CTR is exactly 3.10 on all 14 days.** Real data would vary day to day, so the daily file may be smoothed or synthetic.

**Not checked**
- Raw event data, the bucketing code and the source of the assignment mismatch.
- Whether the daily file is real or processed.
- Variance and confidence intervals, which aren't in the files.
- Segment-level effects.

**Recommendation:** Don't ship v7. Write it up as a learning, as the plan requires. Next steps:
1. Find the cause of the sample ratio mismatch.
2. Investigate the +38 ms latency regression.
3. If the team still wants v7, rerun with a fixed split and a longer ramp-in period so the novelty effect washes out.
