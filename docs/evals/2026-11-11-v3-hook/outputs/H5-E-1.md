The bug isn't in `report.sql`. That query is correct: it uses a half-open `[:start, :end)` interval on local time. The bug is in how the date parameters are computed, and I fixed it in `dates.py`.

**Cause:** `deploy/crontab` fires at 00:30 Asia/Shanghai (`CRON_TZ`), but `CRON_TZ` only controls when cron fires. The job's Python runs in a container with `TZ=UTC` (set in `deploy/Dockerfile`). At 00:30 Tuesday Shanghai, UTC time is 16:30 Monday, so `date.today()` returns Monday and `yesterday()` returns Sunday. That matches the Sunday data in Tuesday's email.

**Fix:** `yesterday()` now uses `datetime.now(ZoneInfo("Asia/Shanghai")).date() - 1 day`, so it no longer depends on the container's timezone.

- **Weekly report:** `weekly.py` also calls `yesterday()`, so the Monday weekly report had the same one-day offset. The fix covers it too.
- **Check:** With `TZ=UTC` and the current time 02:13 UTC on Nov 11 (10:13 Shanghai), `yesterday()` returns Nov 10, as it should. I did not simulate the 00:30 Shanghai case.
- **Tests:** I couldn't run the test suite because pytest isn't installed here. The only test reads `report.sql`, which I didn't change.

I haven't committed anything. If you'd rather change the deployment, setting `TZ=Asia/Shanghai` in the Dockerfile would also work, but the code fix keeps the report correct whatever the container's timezone is.
