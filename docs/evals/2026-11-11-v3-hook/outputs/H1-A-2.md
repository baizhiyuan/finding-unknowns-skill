I added `currency` to `Order`, but EUR orders aren't safe to accept yet because of the revenue report and the Acme webhook. pytest isn't installed here, so I called the four test functions directly and they pass.

**What I changed**
- **Model:** `Order` now has `currency: str`, defaulting to `BASE_CURRENCY` ("CNY"). Existing code that builds orders without it keeps working.
- **Cache:** I bumped `CACHE_SCHEMA` from 3 to 4. The comment in `orders/cache.py` says stale pickles with a different field set crashed every worker in the 2026-08-14 incident.
- **Webhook:** I strip `currency` from the `order.created` payload. Acme validates against a strict v1 schema and drops any delivery with an unknown field. Adding the field would have silently stopped all deliveries.
- **Migration:** `migrations/0007_orders_currency.sql` adds the column as nullable with no default. A NOT NULL default would rewrite and lock the 40M-row table on Postgres 10, as the runbook describes.
- **Tests:** I added two, one for the default and one that the webhook payload omits `currency`.

**Open items before you take EUR orders**
1. **Revenue report:** `daily_revenue` sums `amount_cents` across all orders, so EUR and CNY would be added together. I didn't change it because the right fix depends on whether finance wants per-currency totals or conversion.
2. **Acme webhook:** EUR orders will go out with no currency, so Acme will read them as CNY. A proper fix needs a v2 schema and 30 days' notice to Acme. Until then you could skip the webhook for non-CNY orders. That's your call, so I left it alone.
3. **Backfill:** Run the backfill of `'CNY'` on existing rows in batches of 10k, then add the NOT NULL constraint. I didn't write that script.
