# ranker-v7 launch review

**Recommendation: don't ship v7 as built.**

The plan was approved on 2026-10-12, before launch. Its ship rule is: "primary metric significantly positive (two-sided, alpha 0.05) AND every guardrail passes. Anything else: do not ship; write up as a learning." Revenue per session is the primary metric, and CTR is only "secondary, diagnostic". Both parts of the rule fail:

| Check | Result | Verdict |
|---|---|---|
| Revenue per session (primary) | 4.82 → 4.76, -1.2%, p = 0.21 | Not significantly positive |
| Latency p95 (guardrail, limit +20 ms) | 212 → 250 ms, +38 ms, p < 0.001 | Violated |
| CTR (secondary) | 3.10% → 3.41%, p = 0.03 | Not a ship criterion |

The CTR win is a novelty effect that faded. From `results/daily.csv`, treatment CTR is 3.85 on days 1–3, 3.65 on days 4–7 and 3.12 on days 8–14, against a flat control of 3.10. By week two the lift is about +0.02 pt, so the +10% comes almost entirely from week one. The decay fits the daily series, but I haven't tested it with a new-versus-returning-user split.

## Problems with the data
These weaken even the CTR claim.

1. **Sample ratio mismatch.** The split was planned 50/50, but assignment is 52,310 control against 47,690 treatment. That gives chi-square ≈ 213, far beyond chance. Randomization or logging is broken, so every comparison is suspect. One candidate cause is that the slower v7 loses users before assignment is logged; I haven't checked it. If this is a defect, the right verdict is "rerun", not "v7 lost".
2. **Control CTR is exactly 3.10 on all 14 days.** Real traffic doesn't do that, so the daily file looks smoothed or synthetic. I can't compute a confidence interval for the late-period lift from it.
3. **Rows 5–20 of `metrics.csv` look like placeholders.** Control values run 1.00, 1.10, 1.20 and so on. Every delta is +0.3%, and the p-values rise in steps of 0.04. Don't cite them until their source is checked.
4. **Multiplicity.** 20 metrics were tracked. CTR at p = 0.03 is the only one near significance, and it isn't corrected for multiple comparisons.

## Not checked
- Whether revenue per session was powered to detect a realistic effect. There's no power calculation in the repo, so p = 0.21 may only mean "can't tell".
- What causes the +38 ms (model size, feature fetch, caching).
- Segment results. The relevant rows are the suspect ones.

## Next steps
1. Find the root cause of the sample ratio mismatch.
2. Profile the latency regression. v7 needs to get under +20 ms to be able to pass the guardrail.
3. If v7 is revised, run a new pre-registered test on fresh traffic. Keep revenue per session as the primary metric and run at least 3 weeks, so the novelty window doesn't dominate. Report days 8 and later separately.

I did not run an independent audit of this analysis. It's a single pass over six small files.
