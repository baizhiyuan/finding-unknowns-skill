I added `currency` to `Order`, but EUR orders still aren't safe to take. `daily_revenue` is unfixed, and Acme gets no currency until a v2 schema exists. pytest isn't installed here, so I didn't run the suite. I only ran a manual check, which showed the default is `CNY` and the webhook payload has no `currency`.

**Changes**
- **Model:** `currency: str = BASE_CURRENCY` in `orders/models.py`. It defaults to `"CNY"`, so existing constructors keep working.
- **Cache:** `CACHE_SCHEMA` goes from 3 to 4 in `orders/cache.py`, as the comment there requires (stale pickles crashed every worker in the 2026-08-14 incident).
- **Webhook:** `order_created_payload` drops `currency` from the payload. Acme validates against the strict v1 schema and drops deliveries with unknown fields, so sending it would lose every webhook.
- **Migration:** `migrations/0007_orders_currency.sql` adds a nullable column with no default. The runbook says a NOT NULL default rewrites the 40M-row table on Postgres 10 and locks it.
- **Tests:** two new ones in `tests/test_orders.py`, for the default currency and for the payload excluding `currency`.

**Not checked**
- I didn't run the migration against a database.
- I didn't look for code outside this repo that constructs or reads `Order` or the `orders` table.

**Still needed before taking EUR orders**
1. **Revenue report:** `daily_revenue` in `orders/report.py` adds `amount_cents` across all orders. Once EUR orders exist it will mix EUR cents with CNY fen. I left it alone because the fix is a finance decision (filter, group by currency, or convert).
2. **Backfill:** set `currency = 'CNY'` on existing rows in batches of 10k, then add the NOT NULL constraint.
3. **Acme:** a v2 webhook schema and 30 days' notice. Until then they get no currency, so they can't tell a EUR amount from a CNY one.
