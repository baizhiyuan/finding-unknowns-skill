`Order` now has a `currency` field that defaults to `BASE_CURRENCY` ("CNY"). The four tests pass when run directly, since pytest isn't installed here. I haven't committed anything.

Because the field touched four other things, the change is wider than one line:

- **`orders/models.py`:** `currency: str = BASE_CURRENCY`, placed last so existing constructors still work.
- **`orders/webhook.py`:** `currency` is left out of the `order.created` payload. Acme's v1 schema rejects unknown fields and drops the delivery, so sending it would have lost every webhook. A test covers this.
- **`orders/cache.py`:** `CACHE_SCHEMA` goes from 3 to 4, as the comment in that file requires, so workers don't unpickle old `Order`s.
- **`orders/report.py`:** `daily_revenue` now takes a `currency` argument (default CNY) and only sums orders in that currency. Adding EUR and CNY amounts would give a meaningless total. A test covers this.
- **`migrations/0007_orders_currency.sql`:** adds the column as nullable with no default, per the runbook, so the 40M-row table isn't rewritten or locked. I haven't run it.

Things you still need to do or decide:

1. **Backfill and constraint:** The migration only adds the column. Existing rows are NULL until you backfill them to `'CNY'` in batches of 10k and then add `NOT NULL`. Any code that reads `currency` from the DB must treat NULL as CNY until then. No DB-loading code exists in this repo, so I couldn't check that.
2. **Acme:** They won't see the currency until there's a `webhook_order_v2.json` and 30 days' notice. Until then they would read a EUR order's `amount_cents` as CNY fen, which is wrong. You may want to hold EUR orders from Acme or tell them first.
3. **Finance dashboard:** `daily_revenue` called with no arguments now leaves EUR out of the total. If finance needs EUR revenue, someone has to call it per currency. Converting between currencies would need an FX rate source, which this change doesn't touch.
