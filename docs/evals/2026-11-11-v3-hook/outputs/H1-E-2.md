`Order` now has a `currency` field, defaulting to `"CNY"`. The 5 tests pass, but I ran them with a plain-Python loop because pytest isn't installed here. Nothing is committed.

Adding the field alone would have broken several things, so I changed these too:

- **Webhook** (`orders/webhook.py`): the payload is built from `asdict(order)`, so `currency` would have gone to Acme. Their v1 schema rejects unknown fields and drops the delivery. I strip `currency` from the payload, and a test covers it.
- **Cache** (`orders/cache.py`): I bumped `CACHE_SCHEMA` from 3 to 4. The comment there says stale pickles crashed every worker in the 2026-08-14 incident.
- **Migration** (`migrations/0007_orders_currency.sql`): this adds `currency text` as nullable with no default. On Postgres 10, a `NOT NULL DEFAULT` would rewrite the 40M-row table, as in the 47-minute outage. I haven't run it. The backfill to `'CNY'` (batches of 10k) and the `NOT NULL` constraint still need separate follow-up steps.
- **Revenue report** (`orders/report.py`): `daily_revenue` summed raw amounts, which would have added EUR cents to CNY fen. It now counts only CNY orders, so EUR revenue is left out of the dashboard until you decide how to handle FX.

Two decisions for you:
1. Acme will receive EUR orders with no currency, so they'd read the amounts as CNY. Fixing that needs a v2 schema and 30 days' notice to Acme. Until then, you may want to hold EUR orders back from that webhook.
2. Finance needs to know EUR is excluded from the dashboard total, or you can add per-currency totals.
