`Order` now has a `currency` field, but EUR orders aren't safe to take yet. Nothing is committed. I ran the 5 tests by calling them directly (pytest isn't installed here), and they pass.

**What I changed**
- **`orders/models.py`:** added `currency: str = BASE_CURRENCY`. It defaults to `"CNY"`, so existing callers and legacy rows behave as before.
- **`orders/cache.py`:** bumped `CACHE_SCHEMA` from 3 to 4, as the comment there requires. Without the bump, workers would unpickle old Orders and crash, as in the 2026-08-14 incident.
- **`orders/webhook.py`:** `currency` is stripped from the payload. `asdict(order)` would otherwise send it to Acme, whose strict v1 schema would reject it and drop every delivery.
- **`migrations/0007_orders_currency.sql`:** adds `currency` as a nullable column with no default. I wrote it but didn't run it. `docs/runbook.md` warns that a `NOT NULL DEFAULT` locks the 40M-row table for about 47 minutes.
- **`tests/test_orders.py`:** three new tests covering the CNY default, a webhook payload that stays valid against v1 for a EUR order, and the cache bump.

**Before taking EUR orders**
1. **Acme webhook:** a EUR order's `amount_cents` goes to Acme with no currency, so they'd read it as CNY. Fixing that needs a v2 schema and 30 days' notice to Acme. Alternatively, you could hold EUR orders back from the webhook. Which do you want?
2. **Finance report:** `daily_revenue` adds all amounts together, so EUR and CNY would be summed as if they were the same unit. I left it alone because the right behavior (per-currency totals, converting, or CNY only) is a finance decision.
3. **Migration:** someone needs to run `0007`, then backfill existing rows to `'CNY'` in batches of 10k, and only after that add any constraint. I haven't done any of that. Run it yourself or tell me to prepare the backfill script.

Nothing in the repo creates a EUR order yet, so the risk starts when order intake begins accepting EUR. I'd settle items 1 and 2 before that.
