`Order` now has a `currency` field, defaulting to `"CNY"`. pytest isn't installed here, so I called the three test functions directly, and they pass. I haven't run the migration against a database.

What I changed:
- **`orders/models.py`:** added `currency: str = "CNY"`. The default means existing constructors keep working.
- **`orders/cache.py`:** bumped `CACHE_SCHEMA` from 3 to 4. Its comment requires this on any field change, because stale pickles crashed the workers in the 2026-08-14 incident.
- **`orders/webhook.py`:** the payload now drops `currency`. Acme's v1 schema rejects unknown fields and drops the whole delivery, so sending it would have lost every order webhook. The field can go out once there's a v2 schema, which per `docs/partners.md` needs 30 days' notice to Acme.
- **`migrations/0007_orders_currency.sql`:** adds the column as nullable text with no default. The runbook warns that a NOT NULL default locks the 40M-row table for about 47 minutes on Postgres 10.
- **`tests/test_orders.py`:** added a test that `currency` stays out of the webhook payload.

Before you take EUR orders:
1. **Backfill and constraint:** backfill existing rows to `'CNY'` in batches of 10k, then add the NOT NULL constraint. I left both out of the migration. Until then, whatever loads orders from the DB must treat NULL as CNY.
2. **Revenue report:** `daily_revenue` in `orders/report.py` still sums `amount_cents` across all orders. Once EUR orders exist, it will add EUR cents to CNY fen and produce a wrong total. It needs to group by currency or convert. I left it alone because that's a finance decision.
3. **Acme v2:** the webhook change means Acme won't see the currency of EUR orders until v2 exists. They will receive EUR amounts as if they were CNY. You may want to coordinate with them before going live.
4. **`BASE_CURRENCY`:** the comment on it in `orders/settings.py` ("every order so far is in CNY") will stop being true once EUR orders start.

I haven't committed anything.
